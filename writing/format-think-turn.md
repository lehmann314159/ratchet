This one drops one level further — into the actual wire-level mechanics of a single call to a model, where almost everything the first two pieces describe turns out to originate.*

## The call underneath the call

Every verb in Ratchet — WRITE, CRITIQUE, JUDGE, ADJUDICATE, all of them — eventually reduces to one of two functions in a small Go client: `Chat`, a single request-response exchange, or `ChatWithTools`, a bounded loop of the same exchange with tools attached. Both talk to Ollama's HTTP API, not Anthropic's. That one substitution is the reason this piece exists: Claude's API has spent years absorbing exactly the problems described below into solved, invisible infrastructure. Ollama's hasn't, because nobody built it to run a fleet of open-weight models through a multi-turn structured-decision pipeline at production reliability. Ratchet had to build that layer itself, and building it meant learning — the hard way, incident by incident — what these models actually do at the token level.

## What a turn is

A **turn** is one request-response exchange inside a `ChatWithTools` loop: the accumulated conversation goes out, the model's response — text, a tool call, or both — comes back, and if a tool was called, its result gets appended and the loop goes around again. A verb like REFINE_TESTS_CRITIQUE runs up to six turns; WRITE's turn budget scales with how many functions the bead still needs written; ADJUDICATE's tool turns end the moment its final structured answer arrives.

Every turn also has its own token ceiling, separate from the whole-call timeout: `toolLoopNumPredict`, capped at 8192 generated tokens. The reason is concrete and specific — a reasoning model whose thinking stream doesn't know when to stop can climb past ten thousand tokens and keep climbing, wedging Ollama's single generation slot for the full sixty-minute client timeout while producing nothing usable. One observed case hit 14.5K tokens and was still going before this cap existed. At the cap, Ollama just ends the turn cleanly with `done_reason:"length"`, which lets the calling loop detect the dead turn and recover instead of hanging silently for an hour. Claude Code's own tool loop has a broadly similar turn structure, but it essentially never needs a defense like this — a frontier model reliably knows when it's done thinking.

## Streaming vs. transactional, and why only EXECUTE gets a monitor

Not every verb even talks to Ollama the same way. The one-shot decision verbs — SURVEY, CERTIFY, DECOMPOSE, AUDIT, RECONCILE, ANALYZE, REVISE_PENDING — use a plain, non-streaming call: the whole request goes out, and the whole response comes back as one block once Ollama is finished. The tool-loop verbs stream instead, chunk by chunk. This wasn't the original design — streaming was tried everywhere first, for the observability it buys, and then deliberately reverted on the one-shot verbs specifically, for a concrete reason: streaming a response token by token adds real per-chunk overhead, and on a verb generating thousands of tokens (RECONCILE, in particular), that overhead compounded badly enough to turn a one-minute call into a thirty-minute timeout. Non-streaming lets Ollama batch its own output and send it once, which is simply faster for a call that's going to be parsed as a whole the moment it lands anyway. The tool-loop verbs keep streaming because the opposite is true there: the point isn't speed, it's being able to watch a long generation happen in real time, in the trace file — which is the only reason a stalled or spiraling turn is ever diagnosable at all.

That same logic — a long-running generation is worth *watching*, not just waiting for — is also the entire justification for something no other verb gets: EXECUTE_BEAD, alone, runs alongside a second, independent watchdog process. WRITE, CRITIQUE, and JUDGE are tool loops too, but short, bounded ones — a handful of turns, each capped by the per-turn ceiling above. EXECUTE_BEAD's loop can legitimately run up to 45 minutes and 50 turns, long enough that something watching *while* it happens, rather than only checking in between turns, seemed worth the extra layer. `MONITOR_EXECUTION` is that layer: a second model, separate from the one doing the work, polling the live trace file on its own clock and answering nothing more than one question — should this be killed right now — with the standing authority to actually send the kill signal if the answer is yes.

## `format:"json"`: a grammar, not a suggestion

Ollama's `format:"json"` option isn't a system prompt nudge. It's **grammar-constrained decoding** — every token the model is allowed to sample next is filtered against a JSON grammar before it's chosen, so the model is structurally incapable of emitting anything that isn't on a path to valid JSON. This is a genuinely different mechanism from how Claude produces structured tool calls, which the model was trained to emit reliably in a dedicated format, not forced into one by masking the token distribution at generation time.

That difference is exactly what caused the sharpest bug in this whole layer, already told in the last piece as a story: `qwen3:32b`'s Ollama template requires it to write a tool call as literal `<tool_call>...</tool_call>` text, in the same content channel the JSON grammar was constraining — and `<` is not a legal way to start a JSON value. Not "usually blocked." Structurally, always blocked: zero non-empty tool calls in 139 recorded calls. The general mechanism behind that specific incident is worth naming directly: **whenever a model's tool-calling syntax and a content-format grammar share the same channel, one of them loses**, and which one loses depends entirely on that model's own template — not on anything Ratchet's code does.

## Thinking models: a stream the grammar can't see into

A "thinking" or "reasoning" model produces its chain-of-thought as a distinct pass before committing to an answer — sometimes as its own field in the response, sometimes inline behind a `<think>...</think>` tag. `format:"json"` and a separate thinking pass turned out to be close to mutually exclusive, measured directly: asking a reasoning model for `think:true` plus `format:"json"` produced a real, substantial thinking block — and a `message.content` field containing exactly `{}`. Empty. The grammar mask applies from the very first generated token, and `<think>` isn't valid JSON, so a model that wants to think before answering has nowhere legal to put it.

The only reason the framework's original model fleet ever worked under this constraint is an accident of template design: `gemma4:31b` isn't a reasoning model at all, and the older-style `qwen3:32b` template happens to defer the grammar mask until after its own `</think>` tag closes — think first, close the tag, *then* the JSON constraint kicks in. Every faster, newer reasoning model considered for the fleet broke this coexistence outright.

The fix that actually worked, for the verbs where it applies, is almost elegant: define an explicit JSON Schema for the verb's output whose **first required property is `reasoning`** — a plain string, positioned before any of the verb's real structured fields. Ollama follows a schema's declared property order when generating, so the model's chain-of-thought becomes a grammar-legal string value it fills in *before* it has to commit to the structured decision that follows. The model still gets to think; the thinking just has to happen inside the JSON instead of before it. Measured on the bead-decomposition verb, on the model that had been failing outright: the same model that produced an empty `beads: []` on two straight attempts under bare `"json"` (63KB of output, ~17 minutes each, nothing usable) went to one attempt, about two minutes, nine correctly-structured beads, and a genuinely substantive 1,239-character reasoning field — on the very first live validation run.

## A schema can cap a string's length, at the grammar level

One side effect of this fix needed its own fix. A schema constrains a string field's *type*, not its *length* — and a reasoning model that doesn't know when to stop filled its `reasoning` field to 76 kilobytes before eventually emitting an escape character that broke its own JSON. The natural assumption is that you'd have to catch and truncate this in application code after the fact. You don't: Ollama's schema-to-grammar compiler actually enforces a JSON Schema's `maxLength` constraint at the token level. Tested directly — a schema capping `reasoning` at exactly 400 characters, against a prompt explicitly demanding exhaustive, unsummarized analysis: the response came back at exactly 400 characters, valid JSON, a real verdict still attached, no thrashing. The grammar itself forces the string closed at the cap and lets the model finish the object around it. The production cap ended up set far more generously — 16,000 characters, since genuine deep reasoning on the hardest verbs ran 13–14K characters unprompted — but the mechanism is the same one that stopped the 76KB runaway: a constraint enforced by the sampler, not a length check written after the fact.

## Where the trick stops working

The reasoning-first schema is not a universal fix, and the one case where it actively backfired is worth knowing, because the failure mode is subtle. Applied to the verb that writes tests — a tool-calling verb, whose real output *is* a sequence of `write_function` calls, not a structured decision — the schema gave the model a perfectly grammar-legal way to describe a plan and claim the work was done, entirely in prose, without ever calling the tool that would have actually done it. The completeness gate downstream caught the gap, but the run had already escalated on a bead that should have been trivial. The principle that came out of it: **a reasoning-first schema is for a verb whose output genuinely is a structured decision. A verb whose real output is a sequence of tool calls needs the model actually reaching for those tools, not narrating an intention to.**

That distinction is exactly why, today, the same-looking `ChatWithTools` call is configured three different ways depending on which verb is making it — confirmed directly against the current source, not assumed from the design history above:

- **Structured-decision verbs** (SURVEY, CERTIFY, DECOMPOSE, AUDIT, RECONCILE, ANALYZE, REVISE_PENDING) run the reasoning-first schema, with the model's separate thinking pass explicitly disabled — the schema *is* where the thinking goes now.
- **Tool-loop verbs** (WRITE, CRITIQUE, JUDGE) drop the format constraint entirely. No schema, no bare `"json"`, nothing — just a defensive parse-and-repair pass on whatever text comes back, once tools have actually been used.
- **ADJUDICATE** stays on the plain, unconstrained `"json"` default, because its model's tool-calling is native — routed through a completely separate mechanism in Ollama that the content-format grammar never touches in the first place, so none of the above problems ever applied to it.

Three configurations for calls that look identical from the outside, and the correct one for any given verb isn't a property of the verb at all — it's a property of whichever model happens to be assigned to it this week. That's a real, unresolved tension: nothing today re-derives the right configuration automatically when a model gets swapped in a bakeoff, so it has already quietly broken twice (the same JSON-grammar conflict, hitting two different newly-tried models on two separate later occasions, for the identical underlying reason).

## The cache you don't have to think about, until the hardware you do

One piece of good news buried in all this: Ollama reuses the KV cache — the attention layer's memory of everything generated so far — across turns within a single tool-loop dispatch, as long as each turn's prompt is the previous one with new tokens simply appended, never rebuilt from scratch. Measured directly from the framework's own timing capture: `prompt_eval` time stays flat, a second or two, even six turns into a CRITIQUE loop with a steadily growing transcript. The actual cost of a long multi-turn loop is almost entirely **generation** — the model thinking and answering — not the supposedly expensive act of re-processing a growing prompt from the start every turn. It's a big part of why an alternative local-inference backend was never worth migrating to: the efficiency win it would have offered was mostly already there.

Claude's API solves a related problem — not re-paying for a stable prefix — with an explicit mechanism instead: prompt caching, opted into with deliberate `cache_control` breakpoints, its own write and read pricing, and a defined TTL. Ollama's version is closer to automatic and implicit within one live session; it isn't a knob you reach for, it's a property of how the server already handles a growing conversation.

What *is* a knob, and a consequential one, is `num_ctx` — the context window size sent with every request, which directly caps how much KV cache a single call is allowed to allocate. It's set to 40,960 tokens by default: not the largest window any fleet model supports, but the *smallest* one any of them natively trained on, chosen deliberately so no model pays the quality cost of stretching past its trained context via rope-scaling. That number isn't free to raise casually, either, because of a fact about the actual hardware behind all of this that has no analog when you're calling a hosted API at all: the deployment runs several ~24–35 GB models loaded simultaneously — Ratchet's own execution step and its watchdog run concurrently, by design — sharing one GPU's unified memory pool. Under that pressure, a single GPU gets time-shared across models, and a generation that should take seconds can silently stall for minutes waiting for its turn. Calling Claude's API, this entire category of problem doesn't exist; calling a fleet of local models, it's an ordinary Tuesday, and the framework has to watch for it explicitly.

## A silence the model didn't cause

That last fact is why there's a whole separate watchdog for something that sounds like the same problem as a stalled model, but isn't. The per-bead pipeline already has a mechanism (covered in the last piece) that judges whether a *model* is making genuine forward progress. This one judges something else entirely: whether the *stream itself* is still alive. During one real run, a model's streaming response went completely silent mid-generation — no error, no chunk, nothing — for over thirty-eight minutes, twice in the same run, while Ollama kept responding fine to everything else. The model wasn't stuck; the transport was.

The fix is a pair of simple bounds on the decode loop: ten minutes of silence tolerated before the very first chunk arrives (covering legitimate prompt evaluation on a big context), three minutes tolerated between any two chunks after that (generous enough that a long, slow thinking stream — which still streams incrementally — keeps resetting the clock, but unambiguous once real silence sets in). And critically, when this fires, it doesn't count as a strike against the job the way a real model failure would: it's classified as transient, retried for free, escalating only if the transport itself stays dead across several attempts. A misconfigured or genuinely offline model still escalates promptly; a GPU that was just momentarily busy with someone else's request gets a second try it didn't have to earn.

## Does the monitor still earn its keep?

Worth asking directly, because the honest answer right now is *not as designed* — and this was found by reading the actual code and its own postmortem, not assumed.

First: its model judgment is currently dead code. `MONITOR_EXECUTION` asks its model for a FIRE or NO_FIRE decision under the standard JSON-format constraint, which makes the model answer with something like `{"DECISION": "NO_FIRE", "REASON": "..."}` — but the function reading that response looks for a line that starts with the literal text `DECISION:`, which a JSON object never produces. Every real verdict the model has returned under this configuration has silently fallen through to the hardcoded default of `NO_FIRE`. The watchdog's semantic half — the entire reason a second model's judgment seemed worth having in the first place — has never actually fired once under this bug. What still works are two much narrower mechanical pattern checks bundled into the same file, catching a literal repeated tool call or a stall specifically on `write_file`. In practice, today, `MONITOR_EXECUTION` already *is* a mechanical check. It just still has a model's name on it.

Second: its cost was real enough to cause an actual incident. Left with no cap on its own generation length, the monitor's model — running concurrently with EXECUTE_BEAD's model, on the same single GPU — once spent eleven and a half minutes generating four thousand tokens to answer a yes-or-no question, competing head-to-head with the real work the whole time. The resulting GPU contention didn't just slow things down; it stalled EXECUTE_BEAD's own token delivery for minutes at a stretch, tripped the stream-idle watchdog described above, and produced a flatly wrong diagnosis — logged as "crashed at startup," when what had actually happened was a healthy generation stalled by its own supervisor. A partial fix capped the monitor's own output at 256 tokens, which helped. The deeper fix — parsing the model's actual verdict correctly, polling it less often, or moving it to a smaller model entirely — is written up in detail and explicitly deferred, not done.

So: no, not as originally conceived. The part of this arrangement that was supposed to be different from ordinary mechanical detection isn't currently running at all, and what's left has already quietly become one more mechanical check, at the price of a second model's worth of GPU contention to keep running it. That's not a rhetorical question this piece is posing — it's the actual, current state of the code, and it's exactly the kind of thing this whole series argues you shouldn't take on trust just because it was clearly a reasonable idea when it was built.

## The throughline

None of these are bugs in the ordinary sense — a JSON grammar that blocks a model's only channel for its own trained behavior, a thinking pass with structurally nowhere legal to go, a GPU quietly time-sharing three big models at once. They're the actual shape of what it costs to run a production pipeline on open, self-hosted models instead of a frontier API: every one of these mechanics is something Claude's own infrastructure has already solved, generalized, and made invisible, and every one of them was, for this fleet, a specific incident with a specific model, root-caused and fixed by hand. The primer at the start of this series put it as a question — how far can process and discipline carry you when the model itself isn't the strongest one available. This piece is most of the actual answer to a narrower version of that question: how far can it carry you when you don't even get to assume the *infrastructure* underneath the model is fully solved, either.
