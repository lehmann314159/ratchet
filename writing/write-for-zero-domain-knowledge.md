## The test

Here's the actual bar, stated as plainly as the project itself states it: does a sentence, read literally, pin down exactly one value or behavior — or is it compatible with two or more implementations that a careful, literal reader could each defend?

If a downstream model could land on two contradictory-but-individually-defensible readings of the same sentence, it's ambiguous. Notice what that definition deliberately doesn't say: it doesn't say "ambiguous to a reasonable person," and it doesn't say "ambiguous to whoever wrote it." Almost by construction, the author already has one reading in mind and cannot see the other one — that's what makes an ambiguity gap different from a mistake. Nobody has to be wrong for a spec to be dangerously unclear.

With Claude, this mostly doesn't matter. Hand it "trim trailing whitespace" and it infers the right newline handling from context nine times out of ten, silently, and moves on. Hand the same sentence to a 30-billion-parameter model across a hundred functions and you get a mix of interpretations — not because the model is careless, but because there genuinely are two defensible readings and nothing forces convergence on one. The whole discipline documented here exists to close that gap before a model ever gets the chance to guess.

## A field guide to the gaps

The project keeps a running, growing catalogue of these — eighteen classes as of the last count, each one earned by an actual incident, not invented speculatively. A few are worth walking through in detail, because the shape of each incident is more instructive than the abstract rule.

**Geometry and arithmetic want a computed number, not a formula.** "Moves toward lower row indices" sounds precise. It isn't, not to a model that has to derive Δrow and Δcol from a sentence rather than see them. The fix, and it generalizes past board games: any spec-derived arithmetic — army counts, hash values, ID sequences — needs the actual computed result stated, not just the rule that produces it. When this generalized from a checkers project to a Kafka-partition simulator needing an FNV-1a hash worked all the way through, it stopped being a board-game quirk and became a standing rule.

**Ownership needs to be spelled out at the field level.** Any function returning a pointer, a slice of pointers, or a map has to say explicitly whether the caller gets an independent copy or a shared reference — and if the container is copied but its elements aren't, that distinction has to be stated too. This one is judgment-only; no keyword scan can tell whether nearby prose actually resolves it.

**And the one that recurred the most, and hid the deepest: how a value gets *constructed*, not just what type it is.** This is worth telling as a story rather than a rule, because it happened twice, independently, in the same project, and it was baked into the very code used to *grade* candidate models for correctness.

A toy expression-language VM's design doc showed abstract-syntax-tree nodes as value literals throughout — `ExprStmt{Value: …}`, written as a plain struct, no `&`. The scaffold used value receivers, so both the value type and a pointer to it satisfied the relevant interface — which meant nothing forced a downstream model toward either choice. In one bead, the model implementing the parser picked pointers; the model that had already written the test, working from the same "value literal" doc, picked values. Neither was wrong, technically — both are individually defensible constructions of the same spec — and the mismatch only showed up as a test failure with no clear culprit. A few days later, in the same project, an *entirely different* bead hit the identical defect: an implementation's dispatch logic matched only value types, but every test subtest constructed the equivalent AST node as a pointer, so every call silently fell through to a generic "unknown statement type" error. Two independent beads, two independent models, one un-pinned decision.

The detail that makes this a genuinely sticky class rather than a one-off slip: when the team later built a benchmarking harness and needed a hand-verified "known-good" reference implementation to grade candidate models against, that reference implementation had the *same* pointer/value inconsistency baked into it — value types at one level of the code, pointers at another. Nobody had written it carelessly; the ambiguity in the original spec was load-bearing enough that even a deliberately-careful reference implementation reproduced it. The fix that eventually stuck wasn't "be more careful" — it was a mechanical check, described below, that flags any place a shared type crosses a bead boundary with no explicit pointer-or-value statement attached.

**Then there's the class that judgment review cannot fix, and the finding here is the sharpest one in the whole catalogue.** A phrase like "standard movement rules" or "usual tie-breaking procedure" reads as complete to anyone who already knows what the category means. A chess design doc once described knight, bishop, rook, and queen movement this way — zero actual content, just a category name standing in for the rule. An independent reviewer, working from a fresh read of the whole document with no prior exposure to it, caught six other real problems in the same pass and never once flagged that line.

That's not a reviewer having an off day. The doc's own conclusion about it is worth stating exactly: a reviewer who shares the author's domain fluency has *the same blind spot as the author*, for the identical reason the author didn't notice it writing it — the gap is invisible from inside the shared fluency, not merely unlikely to be caught. This was confirmed, not assumed: after the chess doc was rewritten with every piece's movement axiomatized as explicit rank/file deltas, a second independent review of the rewrite raised zero findings on that section — the fix worked by removing the ambiguity at its source, not by a reviewer eventually spotting it. The practical consequence is unusual for this project, which otherwise leans hard on independent model review as its main quality mechanism: for this one class, judgment review is not a substitute for a mechanical check, full stop. The only reliable catch is a keyword scan — grep the doc for `standard`/`normal`/`usual`/`conventional` sitting next to a rules-or-procedure noun — because the whole failure mode is that a fluent reader, human or model, won't consciously notice anything is missing.

**One more, freshly added and independently corroborated three separate times in one review batch:** when more than one validation check on the same input can fail simultaneously, and each maps to a *different* error, the order in which they're checked has to be stated explicitly. A function with two guards — say, a negative index and an out-of-range length — leaves a caller passing both a negative index *and* an out-of-range length with no way to know which error comes back, unless the doc says so. Every individual guard statement in isolation is correct; they're just jointly silent about precedence. A worked example that exercises each guard one at a time — which most example tables naturally do — never surfaces the overlap at all. This one arrived from three of four fresh reviewers independently flagging it across three different design docs in the same review pass, which is about as strong a signal as this kind of catalogue ever gets that a class is real and recurring rather than a one-off.

## The tooling built to enforce it

None of the above is meant to be held in one person's head across every doc, forever. Three pieces of tooling exist specifically to take as much of this discipline as possible out of memory and put it into a repeatable process.

**`draft-design-doc`** turns rough prose — more than a one-line pitch, less than a fully-interrogated spec — into a draft that follows a fixed seven-section template, with three rules treated as hard requirements rather than matters of judgment:

- Every worked example has to be verified by actually running something — a throwaway script, executed in the same session, with an inline citation of what ran and what it produced. A worked example with no such citation isn't a style nit; it's a compliance failure. The point is to stop a plausible-looking number from entering a spec on the strength of someone's mental arithmetic.
- Wherever the source prose doesn't pin something the template requires — an exact type signature, a coordinate mapping, an enum's literal values — the draft doesn't invent a plausible answer and move on. It goes into a standing "Open Questions" section, quoting the exact underspecified spot, and stays there until someone resolves it.
- Any literal value that has to survive from the doc into a specific bead's spec gets an explicit pin — a bullet naming the exact bead and the exact value — generated automatically rather than left to hope that later paraphrasing preserves it.

**`checkdesigndoc`** is the mechanical half — a scanner that runs the keyword-detectable classes (arithmetic, geometry, symbolic references, the "standard rules" class, a couple of others) against a finished doc and prints a report. It's explicitly built as an over-flagging report, not a gate — something a human reads and dismisses or acts on, never a pass/fail oracle a project can't start without satisfying. What's more interesting than the check itself is how it got tuned: the first version of the arithmetic check flagged any "identifier operator identifier" pattern and lit up on every single Go pointer type in the codebase (`g *Game` reads exactly like an arithmetic expression to a naive regex). It was rebuilt to trigger only on actual arithmetic-language keywords — "sum of," "the formula," "FNV," "hash of" — cleared by a computed number nearby. The geometry check went through a similar narrowing: words like "above" and "below" turned out to almost always be ordinary cross-references in these docs, not geometric claims, so they were dropped from the trigger list entirely, while more specific words — "diagonally," "clockwise," "toward the opponent's side" — stayed in. Tuned this way against every real design doc in the project's history, the checker now catches every known-bad bead it was built to catch with zero false positives on the clean ones.

**`check-design-doc`** ties both halves together, and does it in a way that deliberately mirrors the pipeline's own decomposition review one level up. It runs the mechanical scan first, then hands the raw doc — not the mechanical report — to an independent review pass, so that pass forms its own findings before seeing what the scanner already caught. Only after both exist does it reconcile them: anything the mechanical scan flagged that the independent reviewer didn't address gets carried forward as unresolved rather than silently dropped, and the one class judgment can't reliably catch is *always* carried forward regardless of what the reviewer said. Every open item then gets an explicit resolution — accepted, rewritten, or affirmatively waived with the reason recorded inline in the doc — before the doc is considered clear to hand to the pipeline. Nothing about that last step is automatic; the whole point is that a doc doesn't get to start a project by default, it gets there by every flagged item being actually looked at.

## Sizing a bead is a human judgment, on purpose

A design doc doesn't just need precise sentences — it needs to be broken into beads the execution model can actually finish in one sitting, and this turned out to be a case where the "let a model decide" instinct actively backfired.

The naive metric — line count — is wrong. One bead in a compiler project ran about 230 lines and finished correctly on the first try, every time it was tried. A much shorter bead in another project, at roughly 150 lines, escalated to human review across five separate runs before anyone figured out why. Raw size wasn't the variable. The actual signal turned out to be two things multiplied together: how many distinct responsibilities a bead owns, *and* how tightly it's wired into other beads' work. A bead can be big and still safe if it's self-contained; a bead can be modest-sized and still spiral if it both does several distinct things and has to integrate with three or more other beads' outputs. Only the combination — size and integration, both high — reliably predicted trouble; either alone produced false alarms in both directions.

The more interesting decision is *who* gets to act on that signal. It would be natural to let the planning step — the model that turns a design doc into beads — decide on its own when something needs splitting. That was tried, in effect, and it failed for a specific, structural reason: a bead-sizing judgment call requires estimating whether the *execution* model will spiral on a given chunk of work, and the planning model has no reliable way to know that about a different model, any more than it reliably knows when its own reasoning has stalled versus is still converging. Worse, the same design doc, run twice through the identical pipeline, produced two different bead counts purely by chance — one run merged two sections into a single bead and spiraled for three review cycles before finishing; the other kept them separate and finished clean on the first pass. Letting an automated step make a judgment call it structurally can't make reliably turned a design decision into a coin flip.

The fix moved that judgment to the one place it can actually be made well: the human writing the design doc, who has whole-system context and isn't trying to estimate another model's failure modes in the middle of a different task. The numbered list of beads in a design doc's planning section is now treated as authoritative — the automated planning step transcribes it faithfully rather than exercising discretion over it, and a lint (the size-times-integration check above, cleared by a one-line rationale when a human deliberately wants an exception) flags likely trouble before a project ever starts, rather than after it's already burned five runs discovering it the hard way. Calibrated against every bead in the project's history: it catches every case that's known to have actually caused trouble, and flags nothing that's known to have run clean.

## Precision has to survive being rewritten, not just be written once

The last piece is less about writing a doc well and more about what happens to a well-written doc after the pipeline starts working on it — because a value pinned precisely in the original spec can still get lost downstream, at any of several points where a bead's spec gets rewritten.

The pinning mechanism itself is straightforward: a design doc's planning section can carry a bullet naming an exact bead and an exact literal value that bead's spec must preserve verbatim, and that bullet gets mechanically appended to the named bead's working spec. But "named bead" turned out to hide real edge cases. If the doc pins a value to a bead called `compiler` and a later step renames or splits that bead into `compiler-disassembler`, the pin's name-based lookup silently finds nothing — no test fails, no warning fires, the value just isn't there anymore. A bullet that names two beads at once (deliberately, because the same rule governs both) only ever attached to the first name a regex happened to match, leaving the second bead with no protection at all despite being named explicitly. And even once a pin correctly lands the first time, several *later* steps rewrite a bead's spec in the normal course of recovering from a stuck execution — and each of those rewrites turned out to be a place a verbatim pin could quietly vanish unless the injection step was run again, explicitly, at every single one of them.

None of these are exotic bugs; they're the direct consequence of treating "the doc said it clearly" as sufficient, when what actually matters is "the exact bead that needs this value, at the exact moment it needs it, still has it" — after a rename, after a split, after a human rewinds a stuck bead back to a clean state. The fix in each case was the same shape: stop trusting that a value, once correctly placed, stays placed, and instead re-run the placement check at every point downstream where it could plausibly be lost. It's the same principle from the mechanical-gates piece in the last article, applied to prose instead of code: a good decision made once isn't enough if nothing re-verifies it survived everything that happened afterward.

## What this buys, and what it costs

None of this makes the underlying models smarter, and it isn't supposed to. What it does is convert "hope the model interprets this the way I meant" into a series of specific, checkable claims: this number is the one that was actually computed, not implied; this type is built as a pointer or a value, stated once, unambiguously, wherever it crosses into another bead's territory; this bead is small enough and self-contained enough that the model executing it has a real shot at finishing it in one sitting; this exact string, once pinned, is still attached to the bead that needs it even after three rounds of automated recovery have rewritten its spec.

The honest cost is that writing a design doc this way is slower than describing the same system to Claude in conversation — every worked example run through a script instead of trusted from memory, every gap surfaced instead of glossed over, every cross-bead value traced to make sure it's pinned somewhere. That's the actual trade this whole piece has been describing: with a frontier model, ambiguity gets absorbed by judgment, quietly, and mostly correctly. With a fleet of small local models, judgment isn't a resource you get to spend — so precision has to do the job instead, and precision has to be built, checked, and re-verified the same way any other part of a reliable system is.
