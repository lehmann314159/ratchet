This one is about where that precise doc actually comes from — the workflow that turns a paragraph of prose into something the pipeline is allowed to trust.*

## Everything before this piece assumed the doc already existed

The last piece described what a good design doc looks like once it's finished: worked examples verified by a real script, ownership stated at the field level, every construction decision pinned down to pointer-or-value. What it didn't describe is how a design doc gets from a rough paragraph to that state — and for most of the project's history, the honest answer was "a person and Claude talk it through, live, in one conversation." That works. It also isn't repeatable, isn't independently checked, and puts the entire quality bar on however careful that one conversation happened to be.

Three incidents made that gap concrete enough to fix. A tasklist bead churned four-plus `REFINE_TESTS` cycles because a Claude-authored line was ambiguous between shallow- and deep-copy semantics — in the very same authoring session whose own commit message described applying worked-example discipline elsewhere. A connect-four bead lost a full bead's worth of cycles because a worked scenario was added to the doc's test-scenarios section without the matching pin in decomposition notes — correct content, missing plumbing. And a doc for a small web app had pins that were real and correct, but written in a format a later piece of tooling didn't expect, because nothing had checked the format convention against the doc that predated it. None of these were failures of care. They were failures of a process that had no step whose entire job was to check.

## Two skills, not one

The fix keeps drafting and checking as two separate skills — `draft-design-doc` and `check-design-doc` — rather than merging them, and the reasoning is the same reasoning that shows up everywhere else in this project: independence is worth something, but only if it's real. Drafting is authoring work, and Claude is good at it inline, in the same conversation as the person who knows what they want built. Checking a draft is different work, and it only means something if the check is done by something that never saw the draft get written — no memory of the intent behind a sentence, no benefit of the doubt for a phrase that reads clearly to the person who chose the words. Folding both into one step would have made the check faster and made it worthless in exactly the cases that matter most, because those are the cases where the author's own fluency is the reason the gap is invisible.

There's a second reason to keep them separate: a check that only runs on freshly-drafted docs is a check that misses everything already sitting in the project's history. Every one of the project's early design docs was hand-written, before any of this tooling existed. `check-design-doc` runs on either kind — a fresh draft or a doc someone wrote by hand two months ago — because the thing it verifies (is this doc precise enough to hand to a fleet of small models) doesn't care how the doc came to exist.

## Drafting: the same authoring discipline, made repeatable

`draft-design-doc` takes prose — more than a one-line pitch, less than a fully-interrogated spec — and produces a draft against a fixed seven-section template: Overview, Architecture, Data Types and Function Signatures, Behavioral Specification, Domain-Specific Test Scenarios, Cross-Bead Contracts, Decomposition Notes. Three of those are conditional and get omitted entirely rather than left as an empty heading — Architecture for a small enough project, Domain-Specific Test Scenarios when nothing in the doc has geometry a raw array index could misrepresent, Cross-Bead Contracts when no bead's output feeds another bead's input. The section order and headings aren't a style choice: `checkdesigndoc` parses the doc by heading, and `SURVEY_SPEC`/`DECOMPOSE_SPEC` read specific sections by name later in the pipeline, so a doc that drifts from the template silently stops being machine-readable in exactly the places that matter.

Three rules inside that drafting step are written as requirements, not judgment calls, for the same reason the confident-wrong problem shows up everywhere else in this project — a model that's confidently wrong never feels uncertain, so "verify when it seems necessary" doesn't help.

- **Every worked example is verified by actually running something**, in the same session, before it goes in the doc — a throwaway Go program, a shell one-liner — with an inline citation of what ran and what it produced. A Δrow, a hash value, a formatted string that "looks right" from memory doesn't clear this bar; only a number that came out of a real execution does.
- **A gap in the source prose becomes an entry in a standing `## Open Questions` section**, quoting the exact underspecified spot and naming the concrete alternatives a literal reader could each defend — never a plausible guess written in and left unmarked. That section is the durable artifact: it survives with no live conversation attached to it, so a doc drafted from a file dropped in a folder gets the same discipline as one drafted interactively. When the drafting *is* interactive, the open questions additionally get batched into direct questions back to the person who wrote the prose, and each answer gets folded back into the relevant section — but the written section never depends on that happening.
- **Every load-bearing literal gets an explicit pin** — a bullet in Decomposition Notes naming the exact bead and the exact value — generated as part of drafting rather than trusted to survive later paraphrasing. This is the mechanism the connect-four incident was missing.

Before handing off, the drafting step runs the mechanical checker on its own output and resolves what it can: a pin/scenario count mismatch, an oversized bead the checker flags, a bead-size note pointing at an undeclared helper. What it does *not* do is resolve the ambiguity findings itself — those go to the next step untouched, because the whole point of the next step is that it's independent of this one.

## The mechanical scan, and the naive version that didn't work

`checkdesigndoc` is the part of this that runs in milliseconds instead of a model call — a scanner that parses the doc by section, applies a set of keyword-triggered rules, and prints a report. It is explicitly built as an over-flagging report a human reads and dismisses or acts on, never a pass/fail gate a project can't start without satisfying.

The first version of its arithmetic check (class 2 in the project's running ambiguity catalogue — eighteen classes as of the last count, most of them judgment-only) was a plausible idea that turned out to be wrong in an instructive way: it flagged any "identifier operator identifier" pattern, on the theory that this catches spec-derived arithmetic hiding in prose. It lit up on every single Go pointer type in the codebase, because `g *Game` reads exactly like an arithmetic expression to a regex that doesn't know Go syntax. It was rebuilt around actual arithmetic-language keywords instead — "sum of," "the formula," "FNV," "hash of" — cleared when a computed number sits nearby. The geometry check (class 1) went through the same narrowing in the other direction: words like "above" and "below" turned out to almost always be ordinary cross-references in these docs ("as described above"), not geometric claims, so they were dropped from the trigger list entirely, while genuinely spatial words — "diagonally," "clockwise," "toward the opponent's side" — stayed in, cleared by a Δrow/Δcol or an algebraic delta nearby. Tuned this way against every real design doc in the project's history, the checker catches every known-bad bead it was built to catch and flags nothing on the docs already known to be clean — the regression anchor is a pre-fix chess doc restored from git history, which the checker correctly flags twice, against the fixed version of the same doc, which it correctly flags zero times.

Two more classes get the same keyword treatment. Class 6 catches a spec that points at a value instead of stating it — "use the Color type from game-state" instead of "White is Color(-1), Black is Color(1)" — cleared by a literal value on the same line. Class 7 catches a doc that names `main.go` as an output file without ever writing the literal string `package main` anywhere in the doc — a gap `go build` gives zero error signal for, since a wrong package name just produces a static archive instead of an executable, silently. That's five classes total — 1, 2, 6, 7, and one more that gets a fundamentally different treatment, covered next — out of eighteen catalogued; the other thirteen (ownership semantics, protocol-return completeness, guard precedence, and the rest) are judgment-only, no keyword scan reaches them.

Two more checks live in the same tool, outside the eighteen-class catalogue, and catch a different shape of gap. A **construction-form** check looks for a Cross-Bead Contract that enumerates a polymorphic type's variants — `Stmt` is `AssignStmt{…}`, `PrintStmt{…}`, and so on — without ever saying whether an instance is a struct value or a pointer to one. This is the exact defect from the last piece's expression-VM story, where two independently-written beads picked opposite constructions of the same undeclared type and the mismatch surfaced only as a test failure with no obvious culprit; the check exists specifically because that incident showed judgment review missing it twice. A **bead-size** check flags a Decomposition Notes entry that owns four or more functions *and* is wired into three or more prior beads or Cross-Bead Contracts — the size-times-integration signal from the last piece, calibrated against the project's own history until it caught every bead known to have actually spiraled and flagged none known to have run clean.

## Class 17: the one judgment can't catch, and what that means for the process

The last piece told the story of "standard movement rules" — a chess doc's four-word stand-in for real content that an independent human reviewer read straight past, twice, because sharing the author's fluency with the domain means sharing the author's blind spot for what that phrase is hiding. That's catalogued as class 17, and the finding shapes the whole downstream process here in a very specific way: this class is mechanically detectable by a keyword scan (grep for "standard," "usual," "normal," "conventional" sitting next to a rules-or-procedure noun), and judgment review is not treated as a substitute for it — not "usually isn't," but structurally can't be, because the exact thing that makes a reviewer fluent enough to review the doc quickly is the thing that makes them blind to this one shape of gap. Classes 1, 2, 6, and 7 each get a mechanical pre-filter *and* a judgment pass, each catching things the other misses. Class 17 gets the mechanical pass treated as authoritative instead, on purpose — the fifth mechanically-detectable class, but the only one where that's the whole story rather than half of it.

That distinction is why the next step doesn't run its two checks and simply combine the results — it runs them independently and then reconciles them, with one asymmetric rule built in.

## Reconciling two independent opinions, on purpose

`check-design-doc` is the orchestrator, and its shape deliberately mirrors the pipeline's own DECOMPOSE → AUDIT → RECONCILE arrangement, one layer earlier — adversarial review applied to the doc itself, before `SURVEY_SPEC` ever reads it.

It runs the mechanical scan first and keeps every `path:line` hit. Separately, it dispatches a fresh subagent with nothing but the doc and the current ambiguity checklist — not the mechanical report, not any hint about what's already been found, not who wrote the doc or why. That last constraint is not incidental: feeding the mechanical hits into the subagent's prompt before it forms its own opinion would anchor its judgment to what's already been caught, defeating the entire reason a second, independent pass exists. The subagent applies the checklist's general test to every signature, protocol description, and directional or numeric claim in the doc, and is explicitly told that finding nothing is an acceptable result — manufacturing findings to look thorough is treated as its own kind of failure.

Only after both passes exist does the orchestrator reconcile them, and the reconciliation rule is where the asymmetry from the last section shows up mechanically:

- A site both passes flagged becomes one item, sourced "both."
- A site only the mechanical scan flagged is carried forward as its own item, "mechanical only, unresolved" — never silently dropped just because the independent reviewer didn't happen to raise it.
- **Every class-17 hit — the self-describing-category-phrase class — is carried forward regardless of what the subagent said**, because a same-fluency reviewer not raising it is the expected outcome for this class, not reassurance that it's fine.
- A site only the subagent flagged becomes its own item, sourced "judgment."

Every row lands in one consolidated table and starts in the same state: **needs decision**. Nothing is pre-resolved on the strength of one pass agreeing with itself. Resolving a row means one of three things happens, explicitly: the suggested rewrite gets applied, a different answer gets applied, or the item gets affirmatively waived — and a waiver has to be written into the doc itself, as an inline comment naming the reason, so the next run of the check doesn't silently re-litigate something already decided. A class-17 item specifically cannot be waived with "a reviewer would understand what this means," because that sentence is the exact failure mode the class exists to catch — the waiver has to either write the missing rule out or state concretely why the category is genuinely fixed for this particular domain. Clearance is two separate confirmations, not one: the process prints "cleared for `new-project`" only once every row is resolved, and copying the doc into an actual project folder is a second, separate action a person has to take. Nothing about reaching a clean report auto-starts a project.

## What the check found, the first time it ran on real docs for real

The workflow's own design notes are candid that it was written and reviewed before it was ever run against a doc nobody had drafted with the tool already in mind — the theory could have been wrong in a way tuning against a handful of curated fixtures wouldn't reveal. The real test came during burn-in preparation, running `check-design-doc` against four existing docs already scheduled for live runs.

Four independent subagent reviews found twenty genuine ambiguities across the four docs. About fifteen were cases where the doc itself was imprecise but a hand-verified reference implementation happened to do the sensible thing anyway — worth pinning down, but not yet a live bug. The other four were sharper: the reference implementations shared the same defect the doc's ambiguity had permitted. A decimal library's coefficient range was stated as including `math.MinInt64`, but the library's own negation and absolute-value functions can't actually negate that value — the doc's range and the doc's own required operations were quietly incompatible, and the reference implementation built from that doc had reproduced the incompatibility rather than caught it. A retry engine's CLI silently defaulted a malformed delay argument to zero instead of reporting it as bad input. Two more followed the same shape: a spec that read as complete, and a careful implementation that faithfully carried the gap forward rather than noticing it. It's the pointer-versus-value story from the last piece, again, in a different shape — an ambiguous spec doesn't just risk two implementations disagreeing with each other; it can produce one implementation that's internally consistent and still wrong, with nothing in that single build to expose the seam.

The other outcome from that same run mattered more than any single bug: three of the four independent subagents, working on three unrelated docs, raised the same *kind* of gap without being told to look for it — a function or CLI command with more than one validation guard that could fail simultaneously, each mapping to a different error, with the doc never stating which one wins. That's now the checklist's eighteenth class, added because three fresh reviewers converged on the same failure mode independently in one review batch — about as strong a signal as this kind of catalogue ever produces that a class is real and recurring rather than one reviewer's idiosyncratic taste.

## What this piece has in common with the rest of the series

Nothing here makes the model doing the reviewing smarter than the model that wrote the draft — the subagent applying the checklist is drawn from the same fleet described two pieces ago, with the same blind spots any of those models has anywhere else in the pipeline. What changes is the arrangement: drafting and checking never share a memory of the same conversation, a mechanical scan runs regardless of whether the judgment pass seems thorough enough to skip it, and the one class that judgment structurally cannot catch is carried forward whether or not anyone raises it. It's the mechanical-gates principle from the second piece, applied one step before the pipeline even starts — verify against something that isn't another model's say-so, and where nothing mechanical can reach, say so plainly instead of hoping a careful enough reader will.
